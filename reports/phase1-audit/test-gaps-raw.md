## Test Coverage Gaps

### [CRITICAL] Concurrent invoice numbering race is never exercised
- Missing scenario: `InvoiceNumbering` explicitly depends on `BusinessRepository.findByIdForUpdate` serializing concurrent creates under READ COMMITTED (see the class javadoc and ADR-0004), but no test issues two concurrent `POST /invoices` (or two concurrent `InvoiceService.create` calls) for the same business from separate threads/connections and asserts both succeed with distinct numbers, or that the lock actually blocks the second caller until the first commits.
- Why it matters: this is the single highest-risk correctness path called out in the audit brief. A regression that removes the `findByIdForUpdate` lock, changes the isolation level, or reorders the read-then-insert would only surface in production as an intermittent unique-constraint violation (`(business_id, number)`) under real concurrent load — exactly the failure mode the javadoc warns about — and nothing in the suite would catch it. `InvoiceNumberingTest` mocks the repository (single-threaded, one call at a time) and `DomainPersistenceTest`'s numbering test only proves the DB constraint exists, not that the locking strategy prevents the race in the first place.
- Suggested test: a Testcontainers-backed test that opens two transactions/threads, has each call `InvoiceService.create` (or hits `POST /invoices` twice near-simultaneously) for the same business, and asserts the resulting invoices have sequential distinct numbers (e.g. `INV-2026-0001` and `INV-2026-0002`), not a thrown unique-constraint exception. A secondary, cheaper test could assert `findByIdForUpdate` actually blocks: start transaction A, lock the business row, confirm transaction B's `next()` call does not return until A commits.

### [CRITICAL] No test asserts "invoice-already-paid" (409) when a payment is attempted on an already-PAID invoice
- Missing scenario: `PaymentService.record` has an explicit guard — `if (invoice.getStatus() == InvoiceStatus.PAID) throw new ConflictException("invoice-already-paid", ...)` — but every existing `PaymentApiTest` scenario that reaches PAID does so via the *final* payment in the same request that flips the status; none of them then issue one more payment against that now-PAID invoice to prove the guard fires.
- Why it matters: this is a money-safety branch (preventing a double-payment/overpayment past PAID) with zero test coverage. If someone refactors the balance-based check above it and this guard silently becomes unreachable or is deleted, nothing fails. It's also the one branch of the three-part state check (`hasBeenSent`, `== PAID`, `amount > balance`) that isn't exercised at all — the other two are.
- Suggested test: seed a SENT invoice, pay it off in full (or directly set status to PAID + balance 0), then POST another payment (even a nominal S$0.01) and assert 400/409 `/problems/invoice-already-paid` with the invoice untouched.

### [CRITICAL] Deactivating a staff member is never tested against an already-issued JWT on their next request
- Missing scenario: the Tech Scope explicitly flags "⚠️ Staff deactivation: `active=false` must fail token validation on next request (check flag in the auth filter/service, not just at login)," and `AccountStateFilter` implements exactly this by re-reading `user.isActive()` from the DB per request. But no test issues a token for a still-active user, deactivates that user (via `PATCH /team/{id}` or directly through the repository), and then reuses the *original, already-issued* token against a protected endpoint to confirm it's now rejected with 401 `account-deactivated`. `AuthApiTest.deactivatedUserCannotLogIn` only proves deactivation blocks a fresh *login*, which is a different code path (`AuthService`, not `AccountStateFilter`) and doesn't touch tokens issued before deactivation.
- Why it matters: this is the specific bug the whole filter exists to prevent — a token issued before deactivation staying valid until it expires. It's a security-relevant, explicitly-called-out invariant with literally zero coverage of the actual mechanism (stale-token rejection); only the unrelated login-time rejection is tested.
- Suggested test: in a `@Transactional` web test, mint a token for a STAFF user via `TestTokens.bearer`, deactivate that same user through the repository (`user.setActive(false)`), then reuse the original token on `GET /clients` (or any protected endpoint) and assert 401 with `/problems/account-deactivated`.

### [MAJOR] `must_change_password` gating is proven on only one protected endpoint
- Missing scenario: `AuthApiTest.mustChangePasswordBlocksEverythingExceptChangePassword` and `JourneyTest` both only probe `GET /clients` as the "blocked" endpoint. No test hits a spread of endpoint shapes — e.g. `POST /invoices`, `GET /dashboard` (owner-only + gated), `GET /team`, `PATCH /team/{id}`, `POST /invoices/{id}/payments` — with a must-change-password token to confirm the filter blocks all of them uniformly, not just the one that happens to be checked.
- Why it matters: `AccountStateFilter` is implemented generically (any request except the `CHANGE_PASSWORD` matcher), so this is lower risk than the deactivation gap above, but the matcher itself is a hand-written `PathPatternRequestMatcher` for one exact method+path; a typo or an unintended second carve-out added later (e.g. someone permits `GET /auth/me`) would not be caught because only one non-exempt endpoint is ever checked.
- Suggested test: parameterize or list-assert must-change-password rejection across a handful of endpoints spanning different controllers/roles (client, invoice, team, dashboard, settings), not just `/clients`.

### [MAJOR] No test for role-vs-state precedence on the payment endpoint
- Missing scenario: `InvoiceLifecycleApiTest.roleIsCheckedBeforeState` proves that for `/send`, a staff caller on an already-SENT invoice gets 403 (role checked first), not 409. `PaymentApiTest` never runs the equivalent combination — a STAFF token against a DRAFT (or PAID) invoice's `/payments` endpoint, where both the role check (staff can't touch payments) and the state check (draft/paid can't take a payment) would independently fail.
- Why it matters: the precedence rule ("role answers first because `@PreAuthorize` runs before the method body") is a general architectural claim tested for exactly one endpoint family (lifecycle transitions). Payments is a separate controller/service (`PaymentController`/`PaymentService`) with its own `@PreAuthorize`, and nothing proves it follows the same precedence — a regression there (e.g. someone moves the role check into the service, after the state check) wouldn't be caught by any existing test.
- Suggested test: `staffCannotRecordPayments`-style test but against a DRAFT invoice (not a SENT one), asserting 403 `/problems/insufficient-role` rather than 409 `/problems/invoice-not-sent`.

### [MAJOR] GST rate re-registration mid-lifecycle (unregistered → registered) is tested only up to submit, not through to a second send
- Missing scenario: `InvoiceLifecycleApiTest.anUnregisteredBusinessSendsWithoutGstForGood` sends an invoice while unregistered, then registers the business, then attempts to *resubmit* the same (already-SENT, so illegal-transition) invoice and confirms the snapshot is still null. It never creates a **second**, brand-new invoice after the GST registration change and sends *that* one, to confirm the newly-registered rate *does* apply going forward (proving the snapshot logic isn't accidentally "sticky" in the other direction, e.g. via a stale live-computed value cached on the business).
- Why it matters: the existing test only proves "old invoice doesn't retroactively gain GST." It doesn't independently prove "a brand new invoice, created and sent after registration, correctly picks up the new rate" — both halves of the toggle are asserted in `InvoiceTotalsTest`/`SettingsApiTest` in isolation but never chained through an actual `/send` call for a *newly created* invoice post-registration.
- Suggested test: after `businesses.saveAndFlush(acme)` turns on GST, create a fresh invoice via `POST /invoices`, send it, and assert `gstRate`/`gst`/`total` reflect the new rate.

### [MAJOR] BigDecimal HALF_UP boundary is tested with only one three-line 0.005 case, not an exact halfway single value
- Missing scenario: `InvoiceTotalsTest.roundingIsAppliedOnceToTheSubtotal` proves rounding happens once on the subtotal (three lines of 0.005 → 0.02), which is good, but no test exercises a single-value exact-halfway boundary — e.g. a subtotal that lands exactly on `X.XX5` (like 1420.005 or a deliberately engineered 0.125) to confirm `HALF_UP` rounds away from zero as expected, rather than `HALF_EVEN`/`DOWN` sneaking in via a library default. There's also no test with a negative-adjacent boundary (not applicable here since money can't go negative) or with a quantity carrying many decimal places (e.g. `2.333` hours × a rate) to prove `lineTotal = quantity × unitPrice` itself isn't truncated before the subtotal sum.
- Why it matters: HALF_UP vs HALF_EVEN only diverges at exact .5 boundaries, and that's precisely the case with no direct test — the existing test's 0.015 total is not itself an exact boundary at 2-decimal scale after summing (it happens to work out to .015, one specific case). A change to `RoundingMode` or an off-by-one in `setScale` ordering could pass the existing suite while still rounding some genuine .XX5 boundary the wrong way.
- Suggested test: construct a subtotal that is a bare `?.??5` value at the rounding boundary (e.g. one line item priced to produce subtotal `100.125`) and assert the rounded total is `100.13` (HALF_UP), plus a case with a fractional quantity (e.g. `1.5` hours at `$33.33`/hr) to confirm `lineTotal` math isn't independently truncated.

### [MAJOR] Cross-business 404 is untested for `/settings` and for the `/team` collection-level endpoints beyond PATCH
- Missing scenario: cross-business isolation (404-not-403) is proven for invoices, clients, and payments, and for `PATCH /team/{id}` targeting another business's user. It is not proven for `POST /team` (creating a staff member) attempting to reference something cross-business (not directly applicable since business comes from the token, so lower risk) — but more importantly there is no test proving that `GET /settings` for one business never leaks another business's GST/terms configuration, nor a test that a `sentBy`/`recordedBy` reference somehow spanning businesses is guarded. This is a minor/major gap because the settings endpoint's isolation is implicit (scoped by token, no id param) so it's structurally safer, but it's still an unverified assumption.
- Why it matters: `/settings` and the aggregate `/team` list are exactly the kind of endpoint where a future change (e.g. adding a business-switch feature, or a bug in `CurrentRequest`) could leak data across tenants without any id-based 404 check to catch it, since there's no explicit repository lookup test guarding it the way `findByIdAndBusinessId` does elsewhere.
- Suggested test: seed two businesses with different GST settings, call `GET /settings` as each owner, and assert each only ever sees their own configuration (this is implicitly true today but not asserted as an isolation property, only as a "defaults are correct" property).

### [MINOR] Illegal-transition messages are checked for only two of the five statuses
- Missing scenario: `InvoiceLifecycleApiTest.illegalTransitionsExplainThemselves` checks the message wording for one case (PAID → submit). `InvoiceStatusTest` proves the full boolean matrix but never checks the human-readable message text for the other terminal/illegal combinations (e.g. OVERDUE → submit, SENT → reject, DRAFT → itself via `/submit` twice).
- Why it matters: low risk — the message-formatting code (`readable()`) is generic and exercised once, so a wording bug would likely show up regardless of which status triggers it. Still, only one of many possible 409 messages is verified end-to-end.
- Suggested test: table-driven/parameterized test hitting `/submit`, `/send`, `/reject` from a few different illegal source statuses and asserting the Problem Detail body's `detail` field each time.

### [MINOR] No test for submitting/sending an invoice that's mid-edit with zero-quantity or negative line items being rejected at creation
- Missing scenario: validation on `POST /invoices` / `PUT /invoices/{id}` line items (quantity/unitPrice must be positive, presumably `@DecimalMin` or `@Positive`) is skimmed from source but not confirmed tested — `InvoiceApiTest.validationFailuresListTheirFields` only tests an empty `lineItems` array and a null `clientId`, not a negative or zero quantity/unitPrice within an otherwise well-formed line item.
- Why it matters: a negative unit price or zero quantity slipping through would silently corrupt `subtotal`/`gst`/`total` math (e.g. a negative line reducing the total below what was actually delivered) — a money-correctness path, but likely caught by Bean Validation annotations already present, hence minor rather than major/critical pending confirmation those annotations exist.
- Suggested test: POST an invoice with a line item `quantity: "0"` or `quantity: "-1"` / `unitPrice: "-10.00"` and assert 400 naming the field.

### [MINOR] Dashboard's `overdueAmount`/`overdueCount` interaction with a payment that partially pays an OVERDUE invoice isn't directly tested for the overdue-specific figures
- Missing scenario: `DashboardApiTest.headlineStatsMatchTheWorkedExample` includes one partially-paid OVERDUE invoice and checks `overdueAmount`/`overdueCount` once, but there's no test with *two* overdue invoices (to prove `overdueCount` sums correctly rather than coincidentally being 1) or an OVERDUE invoice that gets fully paid (to prove it drops out of `overdueAmount`/`overdueCount` once PAID).
- Why it matters: low risk aggregate-query correctness; `overdueCount` is asserted as exactly 1 in the only scenario that includes an overdue invoice, so a query bug that always returns 1 regardless of actual count would pass.
- Suggested test: seed two distinct OVERDUE invoices and assert `overdueCount` is 2 and `overdueAmount` is their summed balance.

### [MINOR] No test that a rejected invoice's `rejectionNote` is cleared specifically by `/send` (direct DRAFT→SENT), only by resubmission
- Missing scenario: `InvoiceLifecycleService.send` also clears `rejectionNote` (`invoice.setRejectionNote(null)`), but every test that exercises a stale rejection note going away does so via `submit` (resubmission), not via an owner directly sending a previously-rejected DRAFT. No test rejects an invoice, then sends it directly (DRAFT → SENT, skipping resubmission) and confirms the rejection note is gone from the response.
- Why it matters: minor UI-correctness path — a stale rejection note surviving a direct send would be a cosmetic bug, not a money or security one, but it is an explicit line of production code with only indirect coverage.
- Suggested test: reject a submitted invoice (now DRAFT with a note), then call `/send` directly as owner, and assert `rejectionNote` is absent from the response.

### [MINOR] Numbering overflow (9,999th invoice in a year) is proven only at the unit level, never through the HTTP layer
- Missing scenario: `InvoiceNumberingTest.itRefusesToOverflowTheFormat` proves `InvoiceNumbering.next()` throws `IllegalStateException` when mocked to return `INV-2026-9999`, but no web-layer test drives `POST /invoices` into this state (even by seeding a fake highest-numbered invoice directly) and asserts what HTTP status/Problem Detail the caller actually sees — an uncaught `IllegalStateException` might currently surface as a bare 500, which would be a real (if extremely unlikely in practice) production bug with no way to know about it from the test suite.
- Why it matters: minor because 9,999 invoices/year/business is an edge case unlikely to be hit for a portfolio project's scale, but if it ever recurs, whatever the caller currently sees (probably an unhandled 500) is worth knowing about explicitly rather than by accident.
- Suggested test: seed an invoice numbered `INV-<year>-9999` for a business, attempt `POST /invoices` for the same business/year, and assert the resulting HTTP status is deliberate (ideally a handled 409/500 mapped to a Problem Detail, not a raw stack-trace 500).
